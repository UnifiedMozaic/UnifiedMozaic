# ベンチマーク（生成コードの速度を C と比べる）

UnifiedMozaic が出すネイティブコードの速さを、同じ計算を書いた C（`clang -O2 -fwrapv -ffp-contract=off`）と比べます。各ベンチマークは `<name>.um` と `<name>.c` の組で、同じ型で同じ計算をし、同じチェックサムを `print` / `printf` で出します。出力が1つでも違えば `run.ts` は終了コード 1 になります。

| 名前 | 測るもの |
| --- | --- |
| `intmix` | 配列なしのスカラー整数ループ（xorshift64 と u32 の混ぜ合わせ、4億回） |
| `stencil` | `f64[]` 上の3点ステンシル。境界検査と自動ベクトル化 |
| `structs` | 構造体の配列 `Particle[]` を添字で更新するループ |
| `vecpush` | `u32[]` への `push` と、添字で読んで合計 |
| `kernelblur` | `kernel` + `Buffer<f32>` の `dispatch`（ブラーと saxpy）と、普通の C のループ |
| `fib` | 再帰による関数呼び出し（`i32`） |

## 実行

```sh
node bench/run.ts
```

`clang` と Node.js 22.18 以上が必要です。各バイナリを5回走らせ、最短の実時間を表にします。

## 結果

Linux x86_64 のコンテナ（2コア）で測った1回分です。Apple Silicon では数値が変わります（ベクトル命令の幅や分岐予測の違いで、比も動きます）。コンテナなのでばらつきがあり、ratio は ±0.2 ほど動きます（`stencil` は 1.25〜1.6、`vecpush` は 1.55〜1.76 の範囲で出ました）。

| 名前 | C (ms) | UnifiedMozaic (ms) | um / c |
| --- | ---: | ---: | ---: |
| fib | 735.5 | 735.6 | 1.00 |
| intmix | 776.6 | 797.3 | 1.03 |
| kernelblur | 522.6 | 504.3 | 0.96 |
| stencil | 360.9 | 450.0 | 1.25 |
| structs | 572.5 | 344.0 | 0.60 |
| vecpush | 530.2 | 823.0 | 1.55 |

## 見えていること

- スカラー整数・再帰・kernel は C と同等です。
- `stencil` のような、添字が `i ± 定数` の `for` ループは、境界検査をループの外で済ませます（範囲内の区間だけ検査なしの写しを実行）。この変更の前は C の 1.25〜1.65 倍でしたが、いまは約 1.0 倍です。
- `vecpush` は `push` が遅いのが原因です。配列の長さ・容量・データポインタがメモリ上の構造体に置かれたままになり、`push` のたびに読み書きされます。合計のループ側は境界検査が消えてベクトル化されています。
- `structs` で UnifiedMozaic のほうが速いのは、C 側の `||` が分岐になるのに対し、こちらは別の形にコンパイルされているためと思われます（未調査）。

## 制限・注意

- グローバル変数がないため、定数はすべて関数の中に書いています。
- 出力は整数だけです（浮動小数点の合計は `as u64` で整数にしています）。FMA が使えるターゲットで結果がずれないよう、C 側は `-ffp-contract=off` を付けています。
- `kernel` はネイティブではCPUの複数スレッドで実行されます（要素数 4096 以上のとき。スレッド数は `UM_THREADS` で指定可）。添字が `i ± 定数` の Buffer アクセスは、範囲内になる中央の区間で切り詰めを省くのでベクトル化されます。2コアのコンテナで `kernelblur` は C の1スレッドのループの約 0.5 倍の時間（1スレッドに制限すると約 1.0 倍）でした。GPU の速度ではありません。
- C 側の `push` は `realloc` で容量を2倍にする手書きで、`um_array_grow` と同じ増やし方です。

## Apple M4 での結果（2026-11-15、Apple clang 21、10コア）

| name | C (ms) | UM (ms) | um/c |
| --- | --- | --- | --- |
| fib | 481.5 | 522.0 | 1.08 |
| intmix | 595.6 | 594.3 | 1.00 |
| kernelblur | 99.3 | 85.2 | 0.86 |
| stencil | 76.5 | 68.3 | 0.89 |
| structs | 121.0 | 118.8 | 0.98 |
| vecpush | 326.9 | 308.2 | 0.94 |

`kernelblur` をスレッド数ごとに測ると、1: 224 ms、2: 133 ms、4: 97 ms、8: 82 ms でした。**1スレッドでは C（99 ms）の約2.3倍かかっています。** Linux（x86-64、clang 18）では1スレッドで C とほぼ同じでした。

原因の見立て（未確認）: `blur` の `src[left]`（`left` は `i - 1` か `i`）は添字が `i ± 定数` の形ではないので、検査なしの区間でも切り詰めが残り、ループがベクトル化されません。arm64 向けに出力したアセンブリを見ると、`saxpy` はベクトル化されていますが `blur` はされていません。M4 の C コンパイラは C 版の `blur` をベクトル化できているとみられます。添字の取りうる範囲を kernel の中の変数まで追えば解消できるはずですが、まだ実装していません。
